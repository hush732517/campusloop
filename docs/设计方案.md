# 「校园圈 CampusLoop」设计方案

> 面向在校学生、重点考虑新生使用体验的「校园活动与机会」小产品
> 珠海科技学院计算机协会软件部 2026 年秋季纳新第二轮考核 · AI Agent 产品实战
> 时间背景：2026 年 9 月 19 日（周六）

---

## 一、题目梳理（Word 文档关键信息提取）

### 1.1 考核性质

| 项目 | 内容 |
| --- | --- |
| 考核时间 | 2026 年 9 月 19 日 14:00—16:00 |
| 考核形式 | 个人现场完成 |
| 时间预算 | **约 120 分钟**（必须据此做取舍） |
| 允许工具 | AI / Coding Agent（ChatGPT、DeepSeek、Trae、Cursor、Codex、Qoder 等）、搜索引擎、GitHub、技术资料 |
| 技术约束 | 不限语言与框架，**不强制后端或数据库** |

### 1.2 九项硬性基础要求（评分底线，逐条对应）

| # | 要求 | 本方案的对应设计 |
| --- | --- | --- |
| 1 | 必须能真实运行、可操作，不能是图片/PPT/静态页面 | 纯前端单页应用，真实交互与数据流 |
| 2 | 必须实际使用题目 26 条信息，体现学校 / 学院 / 学生自主发布三类来源 | 26 条全部录入为结构化数据，来源三分类 + 来源标签体系 |
| 3 | 用户能方便地浏览、定位、理解信息 | 标签筛选 + 搜索 + 时间轴 + 状态分组 + 场景化排序 |
| 4 | ≥ 2 项真正可用的核心功能，须产生实际结果 | 核心功能 A：发现与筛选；核心功能 B：参与（收藏/报名/日程/导出） |
| 5 | ≥ 1 种用户主动操作信息的方式，且支持学生自主发布并进入正常流程 | 状态众包上报 + 三步发布向导，发布后进入同一列表、同一筛选、同一详情 |
| 6 | 重要操作结果刷新/重开后合理保留 | localStorage 持久化（收藏、报名、已发布、浏览足迹、新生偏好） |
| 7 | ≥ 1 项自主设计的、与真实场景相关的实用/创新功能 | 四项创新：通知合并、信息缺口"待确认"、撞车检测、发布内容体检 |
| 8 | 基本视觉完整性与交互反馈，信息层级清楚，风格统一，流程闭环 | 设计令牌统一视觉；Toast / 骨架屏 / 空状态 / 二次确认；完整闭环路径 |
| 9 | Git 版本管理 + 提交 GitHub | 6 次语义化 Commit + 完整 README |

### 1.3 材料中真实存在的问题（这是产品机会的全部来源）

对 26 条信息逐条分析后，可归纳出 **五类真实痛点**：

**痛点 1｜补充通知与原始通知割裂（最隐蔽、最容易被扣分的坑）**
- 01「蓝桥杯训练营」：原计划 9 月 20 日起每周六 19:00，9 月 24 日 22:00 报名截止。
- 09「程序设计训练营补充通知」：**首次训练改为 9 月 21 日 19:30，地点改至实验楼 A402**，已报名者无需重复提交，报名截止时间不变。
- 20「创新创业项目团队补充说明」：03 的**开发方向名额已满**，现主要补充设计与材料成员，此前投递者无需重复提交。
- 03「创新创业项目团队招募」：开发、设计、材料成员。
- → 若产品把 03 与 20、01 与 09 当作两条独立信息展示，用户会**按过期信息行动**（去报已满的开发岗、周六白跑一趟）。

**痛点 2｜同一天多场活动撞车，新生最容易掉坑**
- 9 月 19 日（考核当日）：15:00—16:30 前端交流会；19:00 AI 应用入门公开课（约 90 分钟）；19:30 网络安全兴趣小组首次交流。
- 9 月 21 日：19:00—20:30 Git 工作坊；19:30 训练营首次训练（实验楼 A402）；19:00—20:30 科研入门分享会；学生发起的 AI 工具搭子（拟晚间）。
- 9 月 20 日：14:30 路演观摩；16:00 羽毛球约球；19:00 学院 AI 产品设计分享会。
- → 时间冲突**题目从未提示，但真实存在**，用户需要被主动提醒。

**痛点 3｜信息不完整，且题目明确禁止编造**
- 06 学习小组：**报名时间未注明**，"满员即止"；限 30 人。
- 16 摄影志愿者：**具体报名截止时间未注明**；长期招募。
- 12 计算机能力挑战赛：**具体费用信息未提供**。
- 22 羽毛球：**场地待最终确认**；23 AI 搭子：**具体地点未确定**。
- 24 兼职：**未提供主办方、地点和完整内容**；25 数码体验：**活动时间、地点未注明**。
- → 处理原则：**标注"待确认"并给出确认渠道，绝不补全数字与地点**。

**痛点 4｜信息状态是动态的，而屏幕是静态的**
- 04 数模分享会：直播 9 月 18 日 19:30 **已结束**，回放**预计 9 月 20 日上传**。
- 17 Python 资料：资料长期开放，但**网盘提取信息有效至 9 月 22 日**，后续统一更新。
- 19 路演观摩：原报名截止 9 月 18 日 22:00 已过，**如现场仍有余位可候补入场**。
- 14 Git 工作坊：需提前预约，**提交报名表不代表最终录取**，以审核通知为准。
- 07 AI 挑战赛：9 月 21 日 18:00 前意向登记，**登记不等同于最终作品提交**，10 月 20 日交作品。
- 15 AI 创意挑战：9 月 23 日交创意方案，9 月 30 日交最终作品，**进入展示环节后可再组队**。

**痛点 5｜开放发布带来的质量与可信度问题**
- 24「校园兼职福利分享」："零门槛、日结"、要求**添加私人微信**、无主办方/地点/完整内容 → **高风险，典型的引流与诈骗话术特征**。
- 25「数码新品体验交流」：标题为技术交流，正文实为**商家优惠与购买链接**，无时间地点 → **广告伪装，中风险**。
- 22、23 为学生真实自发活动，但存在**场地/地点未定**的不确定性 → **正常但需透明标注**。
- → 产品既要**不封杀开放发布**，又要让用户**一眼分辨可信度**，并给发布者**发布前体检**。

### 1.4 评分关注点解读（决定设计优先级）

| 评分维度 | 出题人真正想看的 | 本方案的回应 |
| --- | --- | --- |
| 实用性 | 围绕真实使用问题，减少获取/理解/参与/发布的操作与判断成本 | 每项功能都能回答"它替用户省掉了哪一步判断" |
| 创新性 | 发现题目**没直接写明**但真实存在的问题；不靠功能数量 | 四大创新全部源于痛点 1—5，而非技术炫技 |
| 视觉与交互 | 层级、风格、反馈、流程自然 | 设计令牌 + 状态色系统 + 完整反馈体系 |
| 产品思维 | 从用户/来源/状态/场景/优先级做取舍；处理开放发布与信息质量的关系 | 明确"不做什么"清单 + 来源分级 + 状态众包 + 发布体检 |
| 完整性 | 闭环、可运行、状态保存、测试、README、Git | 见第八、九、十节 |

**关键判断：出题人反复强调"不追求大而全""机械照搬 AI 生成方案会扣分"。因此本方案主动砍掉登录、后端、真实地图、聊天等一切与 120 分钟不匹配的功能，把 80% 精力投在"信息理解"这件事上。**

## 二、目标用户与核心洞察

### 2.1 用户分层

| 角色 | 特征 | 核心诉求 | 设计权重 |
| --- | --- | --- | --- |
| **大一新生（主角色）** | 不熟悉通知渠道、看不懂"主办方/学分/报名审核"、怕白跑、社恐 | "我**能不能**参加？**什么时候截止**？**在哪**？**要不要抢**？" | ★★★★★ |
| 大二大三学生 | 有明确目标（竞赛/科研/项目） | 快速定位高价值机会、管理多个截止时间 | ★★★☆☆ |
| 学生发布者 | 想约球、组队、办小组 | 低门槛发布、内容别被埋、别被当成广告 | ★★★★☆ |

### 2.2 核心洞察（一句话）

> 校园信息的难点**不在于"找不到"，而在于"不敢信、看不懂、来不及"**。
> 因此产品的第一价值不是"收录更多信息"，而是**替用户完成信息可信度判断与状态判断**。

由洞察推导出产品的三条设计信条：

1. **不确定就说不确定**——缺失信息标注"待确认"，并告诉用户去哪里确认。绝不编造。
2. **更正必须看得见**——补充通知不是新信息，而是对旧信息的修正；修正必须叠加在原信息上。
3. **让用户一起维护真相**——平台无法实时掌握线下变化，把"活动还在吗/截止了吗/地点变了吗"做成一次点击的众包上报。

### 2.3 明确不做的事（产品取舍，也是产品思维的证明）

- ❌ 不做登录注册、不做后端与数据库（题目不强制，120 分钟不值得）
- ❌ 不做聊天/私信（安全与合规风险高，非核心场景）
- ❌ 不做大而全的"校园生活门户"（食堂、二手、失物招领）——与本题场景关联弱
- ❌ 不做真实地图与导航（无接口、易失败），改为"楼栋文字 + 校区楼层提示"
- ❌ 不堆砌 AI 聊天问答（容易变成"看起来厉害但没结果"的功能）

## 三、产品定义

### 3.1 产品名称与一句话定位

- **产品名：校园圈 CampusLoop**
- **Slogan：校园机会，看得懂、来得及、用得对。**
- **定位：一个把多来源校园活动与机会"翻译"成新生能直接行动的信息站。**

### 3.2 用户价值主张

| 用户原来的成本 | 产品替他做的事 |
| --- | --- |
| 在群里翻十几条消息、比对哪条是最新的 | **自动合并补充通知**，默认只显示最新有效版本，并标注"已更新" |
| 到处问"这个我大一能去吗""要不要报名" | **一句话结论**：能不能参加 / 要不要报名 / 现在该做什么 |
| 报完名就忘了截止和活动时间 | **日历视图 + 撞车检测 + 截止倒计时** |
| 看到"日结、加微信"不知道能不能信 | **来源分级 + 风险提示条**，高风险内容进入折叠区 |
| 想发个约球信息，不知道怎么写才有人来 | **发布体检**：完整度评分 + 缺失项提醒 + 风险自查 |

### 3.3 三类信息来源的呈现策略（对应基础要求 2）

| 来源等级 | 判定依据 | 视觉标识 | 产品待遇 |
| --- | --- | --- | --- |
| **校/院官方**（编号 02、10、11、21、26 等） | 由学校、学院、正式赛事组委会发布 | 深蓝 `#1D4ED8` + 盾牌图标 + "官方"标签 | 默认展示，参与"官方确认"权重最高 |
| **正式赛事/机构**（编号 12、07、15 等全国性赛事） | 有明确赛事主体与规则 | 蓝紫 `#6D28D9` + 徽章图标 | 标注"费用未提供"等信息缺口 |
| **学生自主发布**（编号 22—25 及用户新发布） | 学生个人发起 | 橙色 `#EA580C` + 人物图标 + "同学发布"标签 | 显示发布者可信度与"待确认"项；高风险内容默认折叠 |

## 四、信息模型设计（技术核心）

### 4.1 结构化数据设计

26 条原始材料被录入为结构化数据（`data/events.js`）。核心字段与设计意图：

```js
{
  id: 'e09',                          // 稳定 ID，供补充通知引用
  code: '09',                         // 题目原始编号，保持可追溯
  title: '程序设计训练营补充通知',
  source: 'official',                 // official | org | student
  publisher: '校园训练营组委会',        // 原文未写明的一律为 null，不编造
  category: 'training',               // 训练营/公开课/招募/竞赛/志愿/资料/交流/活动
  raw: '因场地调整，首次训练改为9月21日19:30，地点改至实验楼A402；……', // 原文逐字保留
  time: {
    start: '2026-09-21T19:30',        // ISO 化，供日历与排序
    end: null,
    endDate: '2026-09-24T22:00',
    recurrence: null,                 // 用于"每周六/每周三/每两周"
    status: 'rescheduled'             // 见 4.2 状态机
  },
  eligibility: { grades: ['all'], requiresSkill: false, limit: null },
  participation: { needSignup: true, signupChannel: null, fee: null, commitment: null },
  location: { raw: '实验楼A402', certainty: 'confirmed', building: '实验楼' },
  completeness: { score: 0.72, missing: ['signupChannel'] },   // 缺口必须显式声明
  amendments: [{ fromId: 'e01', type: 'override', fields: ['time.start','location.raw'], note: '首次训练时间与地点变更' }],
  relatesTo: ['e01'],                // 关系图：修订 / 同一主办方 / 内容相关
  risk: { level: 'none', reasons: [] },
  verification: { confirmedBy: 'official', verifiedAt: '2026-09-19T14:00' }
}
```

### 4.2 信息状态机（把"动态"变成可计算）

```
draft → upcoming → signup_open → signup_closing(≤24h) → signup_closed
      → ongoing → finished → replay_available
      → 特例：rescheduled（已变更）、waitlist（可候补）、pending_confirm（时间待确认）、expired（资源失效）
```

**状态必须由「当前时间 + 结构化字段」计算得出，而非硬编码文本**，这样"刷新页面后状态自动更新"（基础要求 6 的加分体现）。以 9 月 19 日 14:00 为基准日的计算结果示例：

| 编号 | 计算状态 | 依据 |
| --- | --- | --- |
| 02 AI 应用入门公开课 | **今日 19:00 开始** | 9/19 19:00，无需报名 |
| 10 前端经验交流会 | **今日 15:00 进行中/即将开始** | 9/19 15:00—16:30，无需报名 |
| 04 数模分享会 | **已结束 · 回放待上传** | 9/18 已直播，回放预计 9/20 |
| 19 路演观摩 | **报名已截止 · 可候补** | 原截止 9/18 22:00，现场余位可入 |
| 01+09 训练营 | **已变更 · 报名中（9/24 22:00 截止）** | 首次训练 9/21 19:30 @实验楼A402 |
| 17 Python 资料 | **可用 · 9/22 后失效** | 网盘提取信息有效至 9/22 |
| 24 兼职分享 | **高风险 · 已折叠** | 无主办方/地点，"零门槛日结"+"私人微信" |
| 25 数码体验 | **疑似推广 · 已标注** | 标题技术交流，正文为商家优惠与购买链接 |

### 4.3 关系图（支撑"通知合并"创新）

```
e01 蓝桥杯训练营  ←override— e09 补充通知（时间/地点）
e03 双创团队招募  ←override— e20 补充说明（开发岗已满）
e23 学生 AI 搭子   —related—  e02 AI 公开课 / e18 网安小组（同为 AI 学习场景）
e26 语言角         —related—  e23（同为自由交流型）
```

## 五、功能设计

### 5.1 功能全景（按优先级排序，P0 必做）

| 优先级 | 模块 | 说明 | 对应要求 |
| --- | --- | --- | --- |
| **P0** | 发现页（列表/卡片） | 搜索、分类筛选、来源筛选、状态筛选、排序 | 要求 3 |
| **P0** | 活动详情页 | 结构化字段 + 一句话结论 + 原始文本对照 + 收藏/报名 | 要求 3、4 |
| **P0** | 参与管理（我的） | 收藏与报名、截止提醒、日程、导出 `.ics` | 要求 4、6 |
| **P0** | 发布向导 | 三步表单 + 发布体检 + 进入同一流程 | 要求 5 |
| **P1** | 状态众包上报 | 用户一键上报"已截止/地点变更/活动取消/仍可参加" | 要求 5 |
| **P1** | 时间轴与撞车检测 | 按日聚合 + 冲突高亮 | 要求 7 |
| **P1** | 新生模式 | 三问引导 + 推荐排序 + 术语翻译 | 要求 7 |
| **P2** | 信息体检报告 | 顶部提示缺口、过期、风险统计 | 要求 7 |

### 5.2 页面结构与用户流程

底部/顶部四 Tab（移动优先，桌面居中 480→1100px 自适应）：

```
① 发现    ② 日历    ③ 我的    ④ 发布
```

**流程 A｜新生第一次使用（目标 60 秒内找到一件今天能参加的事）**
```
打开 → 顶部"今天是 9/19，今天有 3 场活动"当日卡
     → 三问引导（年级 / 感兴趣方向 / 每周可投入时间）[可跳过]
     → 发现页个性化排序 + "推荐理由"标签
     → 点开卡片 → 详情页"一句话结论"
     → 收藏 or 报名 → Toast 反馈 → 我的页可见
```

**流程 B｜发现并处理一条被更正的信息**
```
发现页看到 01 训练营卡片，角标"信息已更新"
  → 详情页顶部黄色提示条："本活动时间与地点已变更（9/21 19:30 · 实验楼A402），
     原计划 9/20 起每周六 19:00 · 报名截止 9/24 22:00 不变"
  → 展开"通知记录"查看 01 与 09 两条原文
  → 一键加入日程
```
> 这是本产品最核心的差异化场景：**把"两条通知"变成"一个结论"**。

**流程 C｜学生自主发布**
```
发布 → 步骤1 基础信息（标题/类型/来源/人数/费用）
     → 步骤2 时间与地点（日期选择 + "时间待定"开关）
     → 步骤3 参与方式与补充说明
     → 实时"发布体检"：
        完整度 78%  ⚠ 缺少：具体地点、报名截止时间
        ⚠ 风险自查：正文包含"加微信/日结/链接"等词，可能被判定为推广
     → 发布 → 进入发现页（橙色"同学发布"标识）
     → 我的 → 我发布的 → 可编辑 / 下架 / 查看上报
```

**流程 D｜状态众包**
```
详情页底部"这条信息还准吗？" → [仍可参加] [已截止] [地点/时间有变] [疑似广告]
  → 选择后记入本地并即时更新该条状态徽标 → 我的页可查看我的上报记录
```

### 5.3 四项自主创新功能（详细设计）

#### 创新 1｜通知合并视图（Notice Merge）——解决痛点 1
- **做法**：数据层用 `amendments` 声明"谁修订了谁、修订了哪些字段"。列表与详情默认只显示**合并后的最新有效版本**，被修订的字段打上"已更新"标记。
- **交互**：详情页提供"变更前 / 变更后"对比与"通知记录"时间线（含原文逐字引用）。
- **价值**：用户不必自行判断哪条是最新的，直接消除"按过期信息行动"的风险。
- **为什么算创新**：题目只给了材料，**没有任何一句话提示"这两条通知是同一件事"**。识别并处理这层关系，属于对信息本身的深度理解。

#### 创新 2｜"待确认"信息缺口引擎（Honest Gap）——解决痛点 3
- **做法**：每条信息计算完整度评分，缺失字段显式列出（如"报名截止时间未注明"），并给出**合理的确认建议**（"建议联系主办方或留意后续通知"）。
- **红线**：程序层面禁止生成任何未在原文出现的时间、地点、费用、主办方。
- **价值**：直接呼应用户需求"不擅自编造"，把"不知道"变成一种被良好设计的信息状态。

#### 创新 3｜撞车检测与日程视图（Clash Guard）——解决痛点 2
- **做法**：把"日期 + 起止时间 + 是否需报名"结构化后，自动检测同一时间段的重叠活动；日历页按日聚合，冲突条目高亮并给出取舍建议（"两场都在 19:00—20:30，建议二选一"）。
- **价值**：题目完全未提示，但这是新生最常踩的坑。**零额外数据成本**（数据已结构化），收益极高。

#### 创新 4｜发布体检与风险分级（Post Check-up）——解决痛点 5
- **做法**：
  - 发布表单实时计算**完整度评分**（标题具体性、时间、地点、费用、人数、联系方式、补充说明）。
  - **风险词检测**：命中"日结/零门槛/加微信/私聊/购买链接/返现"等词时给出提示，要求发布者补充主办方与说明，否则内容在列表中带"疑似推广"标识并**默认折叠**。
- **价值**：同时服务发布者（写得更好更容易被采纳）与浏览者（降低判断成本），正面回应"开放发布 vs 信息质量"的矛盾。

## 六、技术方案（面向 120 分钟的现实选择）

### 6.1 选型与理由

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 架构 | **零构建纯静态 SPA**（原生 ES Module + Hash 路由） | 无 `npm install` 失败风险，无构建失败风险，GitHub Pages 直接可用 |
| 依赖 | **不引入任何 CDN 依赖**（手写轻量渲染） | 考场网络不可控，**依赖加载失败 = 作品打不开 = 直接零分** |
| 存储 | **localStorage**（命名空间 `campusloop.v1.*`） | 满足"刷新后保留"，无后端 |
| 数据 | 本地 `data/events.js` 静态结构化数据 | 26 条信息完全可控，可离线运行 |
| 运行方式 | `python -m http.server 5173` 或 VS Code Live Server | 一行命令启动 |
| 部署 | GitHub Pages（main 分支根目录） | 仓库链接即在线可访问作品 |
