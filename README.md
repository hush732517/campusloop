> **校园机会，看得懂、来得及、用得对。**

## 一、运行方式

本作品是**零依赖、零构建**的纯前端单页应用，不加载任何 CDN 资源，因此**离线也能运行**。

### 方式 1：本地静态服务器（推荐）

```bash
cd campusloop
python -m http.server 5173
# 然后浏览器打开 http://127.0.0.1:5173
```

其他等价方式：

```bash
npx serve .          # Node 环境
php -S 127.0.0.1:5173
# 或 VS Code 的 Live Server 插件，右键 index.html → Open with Live Server
```

### 方式 2：GitHub Pages（在线访问）

仓库 Settings → Pages → Source 选择 `main` 分支根目录，保存后访问
`https://<用户名>.github.io/<仓库名>/`。
由于全部资源都是相对路径且没有构建步骤，**无需任何额外配置即可直接部署**。

> ⚠️ 请勿直接双击 `index.html` 以 `file://` 方式打开：浏览器对 `file://` 下的
> ES Module 有跨域限制，脚本不会执行。请使用上面的任一服务器方式。
> 另外 `file://` 环境下 `localStorage` 可能被禁用，导致收藏与发布记录无法保存。

## 二、主要解决的问题

大学生日常会持续接触比赛、项目招募、技术学习、科研、讲座、志愿服务与各类校园活动，
同时学生个人也会自发发布约球、组队、兴趣活动等信息。**开放发布降低了参与门槛，
但信息的质量、完整性和可信度参差不齐。**

在逐条分析题目提供的 26 条模拟信息后，我判断校园信息真正的困难**不是「找不到」，
而是「不敢信、看不懂、来不及」**。具体发现了五类问题：

### 问题 1｜补充通知与原始通知割裂（题目最隐蔽的坑）

| 原始通知 | 补充通知 | 若不合并的后果 |
| --- | --- | --- |
| 01「蓝桥杯」训练营：9/20 起每周六 19:00 | 09：**首次训练改为 9/21 19:30，地点改至实验楼 A402**，报名截止不变 | 周六白跑一趟、不知道该去哪 |
| 03 双创团队招募：开发、设计、材料 | 20：**开发方向名额已满**，现主要补充设计与材料成员 | 去投一个已经满了的岗位 |

**产品处理**：合并为一条最新版本展示，保留「变更前 → 变更后」对比与通知记录时间线；
发现页与日历中，被覆盖的原始通知不再作为独立条目出现（26 条材料 → 24 条有效信息）。

### 问题 2｜同一天多场活动撞车（题目完全没有提示）

我核对了 2026 年 9 月的真实星期（9/19 = 周六、9/21 = 周一），发现确实存在时间重叠：

- **9/19 晚**：AI 应用入门公开课 19:00（预计 90 分钟） ⟷ 网络安全兴趣小组首次交流 19:30
- **9/21 晚**：Git 与 GitHub 工作坊 19:00—20:30 ⟷ 训练营首次训练 19:30 ⟷ 科研入门分享会 19:00—20:30

**产品处理**：结构化时间字段后自动检测冲突，在日历页、当天区块与活动详情页主动提醒，
并给出取舍建议（如「两场都需要报名，建议二选一」）。

### 问题 3｜信息不完整，而题目明确禁止编造

06 学习小组**报名时间未注明**（满员即止）、16 摄影志愿者**截止时间未注明**、
12 挑战赛**费用未提供**、22 羽毛球**场地待确认**、23 AI 搭子**地点未确定**、
24/25 未提供主办方与时间地点。

**产品处理**：一律显式标注「待确认」并列出缺失项，同时给出「去哪里确认」的建议。
**程序层面不存在任何补全路径**——结构化数据中缺失即为 `null`，界面只做标注、不做猜测。

### 问题 4｜信息状态是动态的，而屏幕是静态的

04 数模分享会直播已结束、回放预计 9/20 上传；17 Python 资料网盘提取有效至 9/22；
19 路演观摩报名已截止但现场有余位可候补；14 Git 工作坊报名表不代表录取；
07 意向登记不等同于最终作品提交。

**产品处理**：状态由「结构化字段 + 当前时间」实时计算得出（14 种状态的状态机），
而非写死在页面上的文字。页面顶部的 🕒 按钮可以切换时间基准，直接验证状态推进。

### 问题 5｜开放发布带来的可信度问题

24「校园兼职福利分享」声称「零门槛、日结」并要求添加私人微信，未提供主办方、地点与完整内容；
25「数码新品体验交流」标题为技术交流，正文实为某商家优惠与购买链接。

**产品处理**：来源分级（官方 / 赛事 / 同学发布）+ 风险分级（高风险默认折叠、疑似推广标注）
+ 发布前体检。**不删除、不封杀**，而是让用户知情后自行决定。

## 三、核心功能

### 核心功能 1：发现与筛选 —— 让用户「找得到、看得懂」

- 关键词搜索（标题、原文、关键词、主办方、分类）
- 三维筛选：**分类**（7 类）× **来源**（官方 / 赛事 / 同学发布）× **快捷条件**（今天能去 / 不用报名 / 同学发起 / 适合新生 / 信息待确认 / 信息有更新）
- 5 种排序：智能排序、临近截止优先、按活动时间、最新收录、信息最完整
- **一句话结论**：每张卡片用一行说清「我能不能参加 · 要不要报名 · 什么时候」，
  例如 `全校可参加 · 需报名 · 9 月 21 日 19:30`
- **按紧急度分组**：需要你现在处理 / 报名进行中 / 随时可以参与 / 已结束
- **今日区块**：当天活动置顶，并直接提示时间冲突

### 核心功能 2：参与管理 —— 让用户「来得及」

- 收藏、我要报名，**刷新或重新打开后完整保留**（localStorage）
- 「我的」页四个分区：收藏 / 我报名的 / 我发布的 / 我的上报
- **48 小时内截止提醒**：自动汇总你关注且即将截止的活动
- **导出 `.ics` 日历文件**：真实产出可被手机日历识别的文件，而不是只有视觉效果的按钮
- 浏览足迹、数据导出（JSON）、一键清空

## 四、自主设计的实用 / 创新功能

> 题目要求「至少自主设计并实现 1 项」，本作品实现了 4 项。
> 均来自材料中真实存在、但题目未直接写明的问题，不依赖技术复杂度。

### 创新 1｜通知合并视图（Notice Merge）

把「补充通知」叠加到「原始通知」之上，输出用户真正需要的最新有效版本。
详情页提供变更提示条、字段级「变更前 → 变更后」对比、以及含原文的通知记录时间线。

**为什么算创新**：题目只给了 26 条并列的材料，**没有任何一句话提示这两条通知是同一件事**。
识别并处理这层关系，属于对信息本身的深度理解。这也是我在本题中主动发现并处理的关键问题。

### 创新 2｜「待确认」信息缺口引擎（Honest Gap）

每条信息计算完整度评分（0—100），缺失字段显式列出并给出确认建议。

**关键设计**：把「不知道」当成一种需要被良好设计的信息状态，而不是用猜测填补。
程序层面禁止生成任何未在原文出现的时间、地点、费用与主办方。

### 创新 3｜撞车检测与时间轴（Clash Guard）

自动检测同一时间段的重叠活动，在日历页高亮冲突场次、在详情页提醒冲突对象。

**准确性规则**（否则会产出大量噪音）：
- 同一件事的原始通知与补充通知不算冲突；
- 重叠不足 15 分钟不提示（例如某活动 23:53 结束、另一活动 23:59 截止）；
- 高风险折叠内容不参与。

### 创新 4｜发布体检与风险分级（Post Check-up）

学生发布时实时计算**完整度评分**并检测风险表述：

| 检测项 | 判定 | 处理 |
| --- | --- | --- |
| 日结 / 现结 / 零门槛 / 加私人微信 / 垫付 / 押金 / 索取身份证银行卡 | 高风险 | 发布后标注「高风险」并在列表中默认折叠 |
| 购买链接 / 下单 / 优惠码 / 扫码领 | 中风险 | 标注「疑似推广」 |
| — | 正常 | 正常展示，带「同学发布」标识 |

同时正面回应了「开放发布 vs 信息质量」的矛盾：**不阻断发布，只提示与标注**，
并告诉发布者「怎么写才更容易被同学信任」。命中风险特征的发布，完整度会被封顶
（高风险 ≤ 45 分、中风险 ≤ 65 分）——因为「让人不敢信」本身就是最大的信息缺口。

### 附加：状态众包上报

线下情况随时可能变化，平台无法实时掌握。详情页底部提供一键上报
（仍可参加 / 已截止 / 时间地点有变 / 疑似广告），让用户能主动操作信息。

## 五、主动发现并处理的一项关键问题

> README 要求说明「你在题目材料或产品设计中主动发现并处理的一项关键问题」。

**我选择：第 09 条与第 20 条补充通知对原始信息的覆盖关系，以及由此带来的状态判定问题。**

**发现过程**：
题目把 26 条信息并列成一张表，并说明「材料中的时间、适用对象、参与条件、状态以及
**不同通知之间的关系**，应由你根据题目内容自行判断」。这句话提示了关系判断的重要性。
逐条比对后确认存在两组修订关系：

- 09 → 01：`首次训练改为 9月21日19:30`、`地点改至实验楼A402`，
  同时明确 `报名截止时间不变`（即 9/24 22:00 仍然有效）。
- 20 → 03：`开发方向名额已满`，只保留设计与材料方向。

**为什么它是关键问题**：如果按字面把 26 条当作 26 个独立信息展示，
用户会按**已经失效的信息**行动——去投已经招满的开发岗、按原计划在周六去训练营。
这不是界面问题，而是会直接导致用户损失时间的问题，属于产品必须承担的责任。

**处理方式（数据层 + 界面层）**：

1. 数据层用 `amendments` 声明「谁修订了谁、修订了哪些字段」，支持字段级覆盖
   （`time.start`、`location.raw`）与整体覆盖（`recruitRoles`）；
2. 合并时只覆盖被明确修改的字段，**未提及的字段保持原值**——这正是
   「报名截止时间不变」这句话在代码里的体现；
3. 界面层展示「变更前 → 变更后」对比，并保留两条通知的原文供核对；
4. 发现页与日历中，被覆盖的原始条目不再独立出现，保证「同一件事只占一张卡片」；
5. 撞车检测中排除「互为修订关系」的组合，避免把同一件事误判为时间冲突。

**验证**：`docs/selftest.mjs` 的 T1 / T2 / T10 与 `docs/rendertest.mjs` 的 R2 / R4
对这一行为做了断言，可运行 `node docs/selftest.mjs` 复核。

**同一原则的延伸**：与「不编造缺失信息」共享同一个判断——
**产品对信息的每一次加工都必须可追溯、可核对**。因此详情页始终提供「原文（逐字保留）」区块。

## 六、技术方案

### 选型与理由

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 架构 | 零构建纯静态 SPA（原生 ES Module + Hash 路由） | 无 `npm install`、无构建失败风险，GitHub Pages 开箱可用 |
| 依赖 | **零第三方依赖，不加载任何 CDN 资源** | 考场网络不可控，**依赖加载失败 = 作品打不开**，这是必须规避的致命风险 |
| 存储 | localStorage（命名空间 `campusloop.v1`） | 满足「刷新后保留」，无需后端 |
| 状态 | 由结构化字段 + 当前时间实时计算 | 状态与倒计时自动推进，而非硬编码文本 |
| 测试 | Node 环境自测脚本（自带轻量 DOM 桩） | 无浏览器也能验证领域逻辑、渲染结果与交互链路 |

### 关键实现说明

- **纯函数化的状态计算**：`computeStatus(merged, now)` 与 `findClashes(merged, from, days)`
  把「当前时间」作为参数注入而不是直接读系统时间，因此可以测试 9/18、9/19、9/21、9/25
  等不同时点的表现，也让页面顶部的 🕒 时间基准切换成为可能。
- **逐字保留原文**：每条数据的 `raw` 字段是题目原文的逐字复制，
  产品对它的所有解读都可以在详情页核对。
- **输出转义**：所有来自题目原文与用户输入的内容都经过 HTML 转义后再插入模板，
  用户发布包含 `<script>` 或 `<img onerror>` 的内容不会破坏页面（见 R11 断言）。
- **可访问性**：语义化标签、`aria-current` / `aria-pressed` / `aria-live`、
  键盘可达（Tab / Enter / Space）、`prefers-reduced-motion` 适配、数字键 1—4 快捷跳转。

## 八、下一步最希望完善的内容

1. **接入真实通知源**：从学校官网、学院公众号、第二课堂系统定时抓取，
   用规则 + 语义相似度自动识别「补充通知 → 原始通知」的修订关系，
   而不是依赖人工标注 `amendments`。
2. **服务端共享状态**：目前状态上报只存在本机，只对上报者自己可见。
   理想做法是汇聚到服务端并按「多人一致 / 存在分歧」呈现，
   同时用匿名信誉积分抑制恶意上报。
3. **账号与真实报名打通**：现在是「记录我要报名」，无法真正提交报名表。
   若能与主办方系统对接，就能形成从发现到报名的完整闭环。
4. **发布内容的人工复核通道**：风险分级目前是规则匹配，可能误伤。
   希望增加申诉与人工复核入口，并与学校相关部门建立举报通道。
